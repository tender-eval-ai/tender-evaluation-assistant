# 采购审查助手（Tender Evaluation Assistant）
## Stage I / II Demo 成果汇报

> 演示环境：本地 Docker（前端 Streamlit + 后端 FastAPI），LLM 使用 GitHub Models 免费额度。
> 全程仅使用合成数据；客户真实资料受保密协议约束，只在本地环境处理，从未上云。

---

## 1. 业务解读

**用户与场景**：采购助理需要针对每次招标，审查 20–60 家投标单位的投标文件，
支撑评标小组（TAP, Tender Assessment Panel）出具采购审查报告。

从客户提供的 3 个真实案例（2 个化学品供应类、1 个医疗设备车辆类）及成果样例中，
我们还原了业务流程——评标最多分五个阶段：

| 阶段 | 内容 | 本期范围 |
| --- | --- | --- |
| Stage I | 完整性检查（表格、证书、价格表是否齐备并签署） | ✅ 本期 |
| Stage II | 基本要求符合性（交货期、保质期、包装等 essential requirements） | ✅ 本期 |
| Stage III | 技术评分（marking scheme） | 二期 |
| Stage IV | 价格评分 | 二期 |
| Stage V | 综合得分与排名 | 二期 |
| Price Summary | 价格汇总表（两种格式，见下） | ✅ 本期 |

关键业务发现（决定产品形态）：

1. **每个招标的评审规则都不同**：化学品案例明确"无 marking scheme"，用
   cost-effectiveness（最优投加量 D × 单价 M，越小越好）评价；车辆案例用
   30/70 技术价格加权。规则写在各自的 Terms of Tender 里 → 评审规则必须
   **从招标文件中动态推导**，不能写死。
2. **两种 Price Summary 格式**：格式一为 cost-effectiveness 汇总表（含
   "cannot be calculated / not applicable" 处理）；格式二为单价×数量排名表。
   样例中 TAP 还人工发现了投标人报价总额与单价×数量不符的**算术错误**并加注
   ——这是产品必须复现的审查行为。
3. **投标文件全部是扫描件**（实测 62 页 0 字符可提取），招标文件多为可提取
   文本 → 视觉模型 OCR 是投标侧处理的基础能力，不是可选项。
4. 结论以规范的 TAP 叙述语言呈现（"The TAP found that ..."），报告需可编辑
   Word、英文。

## 2. 产品设计思路

```
招标文件 (文本PDF) ──► [1 摄取] ──► [2 规则推导]  自动生成本次招标的评审 rubric：
投标文件 (扫描PDF) ──►  文本抽取     │            Stage I 清单 / Stage II 基本要求 /
                        或 VLM OCR   │            价格方案与公式（附条款出处）
                                     ▼
                        ★ 人工确认点：rubric 可编辑，确认后才进入评审
                                     ▼
                        [3 逐标提取]  每家投标：文件是否齐备、符合性证据、
                                     │ 价格字段 —— 每条结论均附页码引用
                                     ▼
                        [4 评审计算 —— 纯代码，不经过 LLM]
                                     │ Stage I/II 矩阵、四舍五入规则(2位有效数字)、
                                     │ 币种换算、报价算术复核、排名与推荐
                                     ▼
                        [5 报告生成]  price_summary / summary_list /
                                      evaluation_record （可编辑 Word，英文）
```

三条核心设计原则：

1. **LLM 只做提取与判断，数字全部由代码计算**。价格、排名、算术复核、
   有效数字舍入完全确定性——报告里的每个数字都可复算。
2. **证据优先**：每个"缺件/不符合"结论都带页码与原文引用，评审记录表
   (evaluation_record.docx) 逐格可核查。产品是给 TAP 的**草稿**，不是终审。
3. **人在环节中**：rubric 推导后必须人工确认才能评审；单家投标的提取结果
   可人工修正（修正后不再被模型覆盖）。

**Demo → 生产环境映射**（架构不变，只换推理端点）：

| Demo（本次演示） | 生产（客户本地） |
| --- | --- |
| GitHub Models（云端免费额度） | 客户 DGX Spark 本地 vLLM |
| gpt-4o-mini 文本 / gpt-4.1 视觉 + 降级链 | Qwen3.6-35B-A3B / Qwen3-VL-30B-A3B |
| 笔记本 Docker Compose | 同一套 Compose 部署到 GB10 (arm64) |
| 合成数据 | 真实招投标文件（不出内网） |

## 3. Demo 展示

**演示路径**（前端 4 个页签 = 业务流程 4 步）：

1. **Documents**：上传招标文件与各投标单位文件（每家一个文件夹/PDF）。
2. **Rubric (confirm)**：一键从招标文件推导评审 rubric，人工审阅、编辑、保存。
3. **Evaluation**：批量提取与评审（后台任务、进度可查），展示 Stage I 完整性
   矩阵、Stage II 逐条证据、价格汇总排名。
4. **Reports**：下载三份可编辑英文 Word 报告。

**合成演示案例**（工业除油剂采购，单价×数量方案，3 家投标）故意埋了三个考点：

| 投标人 | 设定 | 系统行为 |
| --- | --- | --- |
| Tenderer_C | 最低价，但**缺 Non-collusive 证书**，且文件为**扫描件** | OCR 后仍判 Stage I 不通过；价格排名第 1 但不获推荐 |
| Tenderer_B | 报价总额有 **HK$500 算术错误** | 复核发现不符并在报告加注；仍为最优合规标，获推荐 |
| Tenderer_A | 完整合规 | 排名第 3 |

产出与客户样例逐项对应：cost-effectiveness 表 / 单价×数量表两种格式、
推荐标加粗、注释自动生成（含算术错误注）、TAP 风格的 Stage I/II 结论段落。

## 4. 可行性结论

**可行**：Stage I / II + Price Summary 的自动化草稿生成在演示环境全链路走通。

支撑证据：

1. **规则推导准确**：从合成招标文件推导的 rubric（4 项清单、3 条基本要求、
   价格方案与数量）与文件条款完全一致，且带条款出处。
2. **确定性计算可靠**：30 项单元测试覆盖舍入规则（2 位有效数字、第 3 位≥5
   进位）、币种换算、算术复核、排名与推荐逻辑；对客户样例中的真实数字
   （如 US$2.97×7.8515→HK$69.96、28,601,670 vs 28,602,400.25）复算一致。
3. **风险面清楚且有对策**：小模型提取曾出现两类错误——把未提及的证书判为
   "存在"、把"30 天交货"误判为不满足"45 天内"。通过提示词强化（present=true
   必须引用原文；数值比较方向显式化）当场修复。这正是设计中"证据引用 +
   人工复核 + 生产环境换更强模型"三道防线的依据。
4. **规模验证**（30 家投标压力测试，经由 Docker 化服务全流程）：

   | 指标 | 结果 |
   | --- | --- |
   | 规模 | 30 家投标（预埋：2 家扫描件、4 家缺证书、3 家保质期不符、3 家报价算术错误） |
   | 全流程耗时 | **287 秒**（创建→上传→rubric 推导→30 家提取→评审→出报告），提取约 9.3 秒/家 |
   | Stage I 判定 | 26/30 通过，4 家缺件**全部命中**，与预埋事实 100% 一致 |
   | Stage II 判定 | 23/26 通过，3 家不符**全部命中**，100% 一致 |
   | 算术错误复核 | 3/3 全部发现并自动加注 |
   | 复合用例 | Tenderer_17 为扫描件且缺证书：OCR 后仍正确判缺件 |
   | 模型降级 | 0 次（主模型全程可用）；"unclear"待澄清项 0 条 |
   | 推荐结果 | 最低价合规标正确胜出（更低价的不合规标被正确排除出推荐） |

   按此速率线性外推，60 家投标约 10 分钟量级（云端免费额度、串行提取）。
   注意：合成文件短且清晰，真实扫描件的 OCR 难度更高——生产准确率以真实
   案例回归集在本地环境实测为准，此结果验证的是**流程与判定逻辑**在规模下成立。

**边界与限制（如实说明）**：云端免费额度限流（OCR 每文档限页）；扫描件质量
影响 OCR 上限；Stage III–V 未实现（二期）；生产吞吐量需在 DGX Spark 实测。

## 5. 需与客户沟通 / 决策事项

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | **Technical Marking Sheet 样例缺失** | 收到的资料中该 xlsx 仅存在 Office 锁定临时文件，需客户补发——它定义"详细评估记录表"的目标格式 |
| 2 | Price Summary 格式适用规则 | 确认理解：由各招标 Terms of Tender 的评价条款决定用哪种格式 |
| 3 | 投标文件目录规范 | 每家投标单位的文件如何交付（文件夹命名、技术标/商务标分卷） |
| 4 | Stage III–V 范围 | 技术评分是否纳入一期 1.0，或作为二期 |
| 5 | DGX Spark 环境 | 部署窗口、网络策略、可否安装 vLLM/Docker（arm64） |
| 6 | 测试数据 | 是否可提供更多脱敏案例作为回归测试集 |
| 7 | 单次审查时效预期 | 决定吞吐设计（夜间批处理 vs 当日出稿） |

## 6. 下一步（第 3–6 周 → 生产 1.0）

1. **正确性加固**：长文档定向检索（防止价格表被截断）、提取结果二次对抗校验、
   汇率表确定性换算、审计日志（模型/提示词/时间戳）。
2. **本地化部署**：DGX Spark + vLLM（Qwen3-VL OCR 批处理、文本模型推理），
   以客户 3 个真实案例建立黄金回归集，实测吞吐。
3. **产品化**：报告版式与客户模板逐像素对齐、批量任务队列与断点续跑、
   多项目管理与权限。
